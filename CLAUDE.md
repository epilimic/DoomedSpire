## How to work with the owner

- Do only what is asked. Do not add features, modes, keys, settings, tools, files or clean-ups that were not requested, even if they seem helpful.
- If something extra looks worth doing, say so in one sentence and wait. Do not build it first.
- If you are not sure of something, ask. Do not guess or assume.
- Do not repeat instructions or re-raise settled items.
- **Never write, rewrite or "improve" Workshop text**: `title`, `description`, `changeNote`, `tags` and `visibility` in `workshop/workshop.json` are edited by hand by the owner only. The one thing a session may do is create that file the first time by copying `workshop/workshop.example.json` to `workshop/workshop.json` as it is (placeholders stay). If a field is missing or still a placeholder, say so and stop. `workshop.json` is git-ignored.
- Never create `workshop/image.png` or `workshop/mod_id.txt`. If the image is missing, remind the owner to make one (PNG, 1280x720 recommended, under 1 MB).
- Never run `workshop/release.sh` or `workshop/upload.sh`: only the owner uploads to Steam.
- Work directly on `main`, never on a branch or a PR, even if the session's own setup names a `claude/...` branch. Only the owner can say otherwise. `git pull` before starting, push when the task is done. Never force-push, never rebase `main`.
- Cloud sessions have no game DLLs, so game-facing code cannot be built here; the owner builds with `dotnet publish`. Say when something is unbuilt, once; do not repeat it after every change.
- The owner's machine is Linux (CachyOS) with the fish shell: `set -x NAME value`, not `export`; `env NAME=value cmd`.
- **Attach the game source at the start of every session:** `add_repo` `epilimic/sts2src`, and read its `CLAUDE.md`. It is a decompiled dump with a generated index and a query tool (`python3 tools/sts2.py find|show|hook|cmd|ui|sym ...`): use the index before grepping blind, cite `file:line` for anything you rely on, and never edit it.
- Game reference source lives in the epilimic/sts2src repo on main. After a game update, read docs/patches/<version>.md there first. It lists breaking API changes, renames and silent balance changes. Compiling against the new DLL isn’t enough: check the “silent changes” section for any mod that touches vanilla content.
- Before solving something non-trivial (lobby networking, UI that needs the game's art, logging, reaching private game members, testing without the game), look in `solutions/` of `epilimic/modding-standards` (index: `solutions/README.md`). If you solve something that looks reusable, say so in one sentence and wait; do not add it unasked.
- Never put secrets in the repo. In a fresh clone, enable the secret-scan hook once: `git config core.hooksPath .githooks`.

## This mod

- Local project path: `/mnt/stuff/sts/doomedspire/`.
- The mod must never break the game: guard every handler and every per-frame callback. (Godot-export mods: the code folder name, `<ModId>Code`, is a Godot script path and must be unique among all installed mods.)
- **Check code with the owner's compiler.** The owner builds with the .NET 10 SDK (C# 14); a cloud container only has .NET 8 (C# 12) until you run `apt-get install -y dotnet-sdk-10.0`. C# 14 treats some code differently (it already broke two lines of the vendored MeltySynth: passing an array now prefers `ReadOnlySpan` overloads, see `src/MeltySynth/SOURCE.md`). Everything under `src/Host`, `src/ManagedDoom` and `src/MeltySynth` is free of Godot and the game, so compile those in a scratch project with `TargetFramework` `net9.0`, `LangVersion` `latest` and `Nullable` `enable`: it must give 0 errors and 0 warnings. The other `src/*.cs` files use Godot or the game and only the owner can build them.
- **Tests:** `dotnet run --project tests/Engine.Tests -c Release` (needs the Freedoom WAD files, see `tests/Engine.Tests/README.md`). It runs the engine, the keyboard and mouse input, the sound effects and the music without the game. Run it after any change under `src/Host` or the engine.
- **No custom Godot classes:** a dll-only mod cannot register scripts, so nothing can subclass a Godot node and override `_Process` or `_Input`. Wire behaviour with signals instead (see `src/DoomView.cs`).
- **Keys: Esc is DOOM's, backtick toggles.** Every key goes to DOOM while it runs, Esc included (it is DOOM's own menu; the menu's Quit Game ends the game and returns to the map, and the next time starts a new one). The backtick key (by label or by position, `KeyMap.IsToggleKey`) is not DOOM's: it toggles between the map screen and DOOM, the game staying in memory where it was (the persistent save state). Inside DOOM `DoomView.OnFrame` reads it from the keyboard state (on press, so a key held from opening does not close it); on the map screen `ToggleHotkey` takes it from `KeyLock`'s rule in front of every game key handler, because the game's dev console opens on the same key (`NDevConsole._Input`) and would open as well. It is only taken once DOOM has been opened in the run (`openedOnce` in `DoomPopup`): before that the backtick is the dev console's key everywhere, as in the game; after, it is the toggle on the map screen and in the DOOM windows and the console's key everywhere else (combat, events, menus). It is only taken when it does something: the map screen open with no capstone screen over it, no dev console showing and no text field focused, or the popup open with no game running yet (picker, message, enemies being got ready), where it closes the popup. While DOOM runs `KeyLock` blocks all keys from the game, so the console cannot open then. There is no Close button: while no game is running (the picker, a message) a click on the map screen's DOOM button, which stays visible under the popup, closes it (`DoomPopup.AttachTo`, the root's `GuiInput`, `DoomView.CanCloseWithButton`); while a game runs every click is DOOM's and only the backtick key leaves.
- **The hotkey legend** (`src/HotkeyLegend.cs`): while DOOM's popup is open, a panel listing DOOM's keys (the toggle shown as ~) is drawn over the map screen's own legend (`%MapLegend`) with the same paper picture, font and colours, under the popup's dimming. The real legend is not changed, so it is back when the popup closes. The rows are the engine's default bindings (`Config.cs`) plus the toggle, shown by their mouse buttons only (M1, M2; Ctrl and Space still work but are not listed); if the keys change, change the rows. The title is red and the rows are 22 pt, each `RowHeight` (37) tall with its text centred, so they spread down the paper evenly.
- **The monitor frame** is the picture `assets/crt.png` with the game on its glass. `src/Host/CrtLayout.cs` has the numbers (`CrtPlacement`: scale 1.44, centred) and the picture's own measurements (`CrtPicture`: glass at 78,78 and 692 x 535 in its 848 x 744 pixels; if the picture is replaced, measure it again). It is placed when the popup opens and when the screen's size changes (`DoomPopup`), there is no live tuner any more. DOOM still steps aside while a canvas layer at or above 100 is showing something (a dev tool such as VfxSpawner's menu, on 128), so the mouse and keys are that tool's (`DoomView.ToolIsOpenOnTop`).
- **The status-bar face is the player's character.** Each playable character has a painted sheet of DOOM's 42 faces (5 health levels x looks, ouch, grin, rampage, plus god and dead) built into the dll, `assets/<character>-faces.png` (`PlayerFace.BuiltInSheet`, `FaceSheetImport`); they go to the engine as an add-on WAD (`face.wad` in the mod's `data` folder) loaded on top of the game, which overrides Doomguy's lumps (`DoomSession.Create(..., extraWads)`). A `<character>-faces-painted.png` in the data folder is used instead of the built-in sheet, for trying one out. Every face is drawn one pixel to the right of where the sheet puts it (`PlayerFace.FaceShift`, done by changing each lump's left offset with `DoomPatch.ShiftRight`, so no pixel is moved or cut and the sheets stay as painted). A character with no sheet gets faces made from its portrait (`src/Host/FaceFactory.cs`, `FaceSettings.Default`; the Defect's is made with `FitWideHead`, `PlayerFace.SettingsFor`: its crown is wider than the face, so the usual crop cut its side lobes off flat and the turned heads stretched into a squared corner; with the setting the whole head is fitted in, a little smaller with room above and below, and every other character is made as before). There are no tuner settings for the faces and no preview; the mod can write a sheet to paint on for every playable character, but this is **off in the release** (`PlayerFace.WriteSheetsToPaintFiles = false`; set it to true to get them back) (`PlayerFace.WriteSheetsToPaint` → `<character>-faces-to-paint.png` in the data folder, one colour, no blood, `FaceSettings.Neutral`, kept while `to-paint.key` matches) with the DOOM health each face stands for written in blue under it (`FaceFactory.HealthLabel`, in a `SheetLabelBand` of 7 pixels under each row, outside every face's box so `FaceSheetImport` ignores it and reads sheets with or without it); `docs/FACES.md` has the layout, the health-level mapping and the rules for editing a sheet. The original face pictures differ in size, so a generated face is drawn once and placed in each lump's own rectangle (see the comment on `FaceFactory.Build`). The two glance faces (`STFST?1`, `STFST?2`) are the whole head moved one pixel left or right. Every lump but the turning ones is made wider than the game's (`FaceFactory.LumpSpec`, used when making faces and when reading a painted sheet): two columns more on the left, so a painted head up to 26 wide (the Defect's) is not cut off, and the glances two more on the right so a head moved either way is not cut off either (columns 2 to 29 of the cell; the turns are 26 wide already); sliding only what is inside the head instead was tried and looked like two faces, one still and one moving, so do not do that. The same add-on-WAD route carries the enemy sprites.
- **STS enemies replace DOOM's monsters, original DOOM 1 games only** (`MonsterSprites.IsOriginalDoom1`: E1M1, no MAP01, none of Freedoom's lumps; DOOM II, Freedoom and every other game keep their monsters). The owner chose each enemy (`EnemySprites.Replacements`, fixed, no randomness; the spectre is the demon's enemy because it is the demon's pictures drawn fuzzy): zombieman = ThievingHopper, shotgun guy = Fogmog, imp = Exoskeleton, demon = Axebot, baron = SkulkingColony, lost soul = TheLost, cacodemon = SewerClam, cyberdemon = KnowledgeDemon (Entomancer was the other candidate; the owner chose KnowledgeDemon after trying them all out by temporarily swapping them into the first levels). Only the living poses (walk, stand, attack, hurt) get the enemy; when it dies it turns into DOOM's own gibs (the owner did not want the enemy's death pose or DOOM's normal corpse): the dying and gibbed frames are eight variations of DOOM's gib animations (the player's, imp's, zombieman's and shotgun guy's, from the engine's state tables, `MonsterSprites.GibAnimations`, `MonsterSpriteBuilder.DeathLumps`), the last frame being the heap that stays; the first two frames of each animation (the creature itself, then its body in pieces) are left out (`FramesBeforeTheBits`) because the owner does not want to see the original monster at all. A corpse's variation is fixed by where the monster was placed (`CorpseVariant`); this needed **one change in the vendored engine**, in `Video/ThreeDRenderer.cs` (marked "DoomedSpire change", listed in `src/ManagedDoom/SOURCE.md`): a corpse picks its picture by that instead of by the side it is seen from. A monster the game data lacks (the shareware game has no lost soul, cacodemon, cyberdemon or spider) is skipped. `src/Host/MonsterSprites.cs` (Godot-free, tested) reads the engine's state tables to say which frame letter is walk, attack, hurt, death or gib, picks a pose for each, and turns captured pictures into sprite lumps named `TROOA0` (rotation 0 = the one picture from every side), all scaled by one amount to the monster's own height and standing on the floor. `src/EnemyCapture.cs` takes the pictures: the enemy's `CreateVisuals()` scene in an off-screen transparent `SubViewport`, held at a moment of an animation (`idle_loop`, `attack`, `hurt`; the game's own names, and failing the exact name one that starts with the same word, `MonsterSprites.ChooseAnimation`: the Knowledge Demon has `attack_light/medium/heavy` and no `attack`; what a creature has is logged when something is missing) after doing what the game does to make a creature's body appear (`SetUpSkin` and `UpdatePhobiaMode`: the Skulking Colony's body is in a skin the game chooses, and was mostly invisible without it), by setting the track time with the state's time scale at 0, read back after `RenderingServer.FramePostDraw` (the pattern of `CreatureAnimator` and `NMapShareButton`). The result is `enemies.wad` (between `S_START` and `S_END`, which is the only place the engine reads sprites from; the last file wins) loaded with the faces. Each frame is given the five lumps `TROOA1`, `A2A8`, `A3A7`, `A4A6`, `A5` (the enemy faces left, so DOOM's sides 2-4 show it as it is and sides 6-8 the mirrored lump, so it faces the way it walks; the picture is cut symmetrically about the standing point so the mirrored one stands in the same place). Starting a game is `async` (`DoomView.BeginGame`) because the pictures take several frames. **Speed and safety:** the finished `enemies.wad` is kept with `enemies.key` (game version from `ReleaseInfoManager`, this build's module id, the DOOM game's name and size, who plays whom) and reused while the key matches and every enemy was drawn, so only the first start after a game or mod update draws anything (delete `enemies.key` to force it); every wait in `EnemyCapture` has a 5 second limit (a hidden or minimized window never draws), the whole job 30 seconds, and what could not be drawn keeps DOOM's picture; if the game will not start with the add-on WADs it starts again without them (`DoomView.BeginGame`). `DoomPalette.Nearest` remembers its answers. A pose that is much taller than the standing one, or far to the side or in the air (`MonsterSprites.IsJumpy`: the Sewer Clam rears up to 151% of its height a quarter of the way into its attack) is retaken at later moments of the animation, up to four steps of 0.1, until it is not. Log tag `enemy`; each enemy also logs one "poses" line (width, height, how far lifted and off centre, as % of the first pose) to find poses that jump about. The owner has seen the enemies working in the game (the clam's jump is fixed, the Skulking Colony renders with its skin).
- **The keycards are the Fool's melody cards** (`src/Host/KeycardTheme.cs`, built by `src/KeyTheme.cs` into `keys.wad`, original DOOM 1 games only, like the enemies): the blue card is the blue Cho Melody (two linked rings), the yellow one the yellow Ki Melody (a cross) and the red one the red Wah Melody (a zigzag); the skull keys are unchanged. The card lying in a level is replaced by the melody's own symbol alone, no card: the game's picture of it (`res://images/packed/fool/symbol_cho.png`, `symbol_ki.png`, `symbol_wah.png`, read in `KeyTheme.ReadGameSymbol`, never stored, nothing drawn by the mod), cropped, scaled so its longer side is `KeycardTheme.SymbolSize` (20) pixels by averaging and put in DOOM's colours (`KeycardTheme.Shrink`: the picture's own colours, or the melody's colour if the picture is white/grey; the second frame a third of the way to white so it flashes; hung with its middle at the item's place and 3 pixels above the floor like the card was). A card whose picture the game does not have keeps the game's own card. The card's icon on the status bar is the same symbol picture made 7 x 7 pixels (`KeycardTheme.IconSize`, `Shrink` with size 7, centred in the square; the skull keys' icons `STKEYS3`-`5` are 7 x 7 too and the slot holds that; the game's own card icons are 7 x 5 and were stretched to look like squares on the 4:3 screen), as `STKEYS0` (blue), `STKEYS1` (yellow) and `STKEYS2` (red), drawn where the skulls' are (offsets 0,0); a card with no symbol picture keeps the game's icon. (`assets/small_cho.png`, `small_ki.png` and `small_wah.png`, the owner's 7 x 5 pictures, are no longer used.) DOOM's palette has no cyan (the nearest colour to Cho's is a light green), so a cyan pixel is shown as the light blue it is closest to (`KeycardTheme.ToPalette`); Wah's pink comes out as the palette's coral red and Ki's yellow exactly. The pickup and "you need" messages name the cards ("Picked up a Blue Cho Melody.", "You need a Red Wah Melody to open this" / "... to activate this", short because the game cuts a message off at the 320 pixel screen edge and does not wrap it; a test checks that every one fits), applied by `KeycardTheme.ApplyTexts` when the game has the marker lump `DSKEYS` and put back by `EngineBaseline` for the next game. The coloured insets of the key doors (patches `W46_37` blue, `W46_38` red, `W46_39` yellow) are left as they are.
- **The game picker is in DOOM's own font** (`src/Host/DoomFont.cs`, Godot-free and tested, made from the built-in game data's `STCFN` letters; `src/DoomText.cs` turns the pictures into controls, one font pixel 3.2 x 3.84 screen pixels like the game's picture): the title twice as big, each game a line of the font (file name only, no size, cut with `...` if too long) with the menu's skull cursor (`M_SKULL1`/`2`, flipped by a timer every 8/35 s) beside the one the mouse is over. There is no instruction text: the screen only shows when the player has saved games (the Workshop page says where). What is listed is `WadLibrary.PickerChoices`: the built-in shareware game ("DOOM shareware") and each saved game, but the shareware game is left out when a saved file is called `doom.wad`. A list longer than fits (`DoomView.BuildDoomPicker` works out how many rows) is a window on it: the mouse wheel moves it a game at a time (the rows' buttons use mouse filter Pass so the wheel reaches the popup root's `OnGuiInput`), and DOOM's `^` arrow, turned over for down, shows above or below only while there is more that way and scrolls when clicked. The font has capitals only (lowercase is drawn as capitals, like the engine). If the font cannot be made the picker falls back to the plain game buttons (`DoomView.ShowPicker`; no scrolling there). A saved game that fails to start (Heretic, Hexen and other non-DOOM games: the engine throws while loading) shows "Sorry, this WAD is not supported." above the list; the error itself is in the log. The other messages in the popup (errors with no picker) are still the game's plain text.
- **The engine's tables are put back before every game** (`src/Host/EngineBaseline.cs`, called from `DoomSession.Create` and at the start of `EnemySprites.TryBuildAsync`): the engine keeps the monsters, weapons and texts in static fields and a game with a DeHackEd patch (Freedoom) changes them in place for good, so the next game in the same run would play with the first one's changes. **Engine changes so far** (each marked "DoomedSpire change", listed in `src/ManagedDoom/SOURCE.md`): the corpse picture in `ThreeDRenderer.cs`, and telling the game from its maps in `Wad.cs` (the engine only knew exact file names, so the built-in `doom1-shareware-1.9.wad` was "undetermined" and offered episodes that are not there, and a registered `doom.wad` was taken for the Ultimate DOOM and failed on the missing picture `M_EPI4`).
